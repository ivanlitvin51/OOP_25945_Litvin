В официальном документе задания («... OOP_05.pdf») работа разделена на 5 шагов,

ЧАСТЬ 5.I: БАЗОВАЯ СБОРКА CMAKE И БИБЛИОТЕКА В ОДНОМ КАТАЛОГЕ

Требования:
  1. Взять базовую реализацию функции вычисления гипотенузы прямоугольного
     треугольника (hypo) и модифицированную функцию со случайным бонусом (hypo_mod).
  2. Разместить функции в соответствующих пространствах имен:
     - hypo_basic — для обычной точной гипотенузы: sqrt(a^2 + b^2);

  1. Модифицировать проект из 5.I так, чтобы библиотека функций находилась

  2. В поддиректории создать свой файл CMakeLists.txt, создающий цель библиотеки.
  3. В корневом CMakeLists.txt подключить поддиректорию через `add_subdirectory()`
     и слинковать с исполняемым файлом через `target_link_libraries()`.

Требования:
  1. Модифицировать проект из 5.II, добавив библиотеку Google Test (googletest).
  2. Расположить тесты в отдельной директории `tests/` со своим CMakeLists.txt.
  3. Написать тесты, проверяющие корректность вычислений обеих функций.
  4. Продемонстрировать запуск тестов как минимум ДВУМЯ РАЗНЫМИ СПОСОБАМИ:
     - Способ 1: Прямой запуск скомпилированного бинарника тестов.
     - Способ 2: Запуск с помощью встроенного в CMake тестового раннера `ctest`.
  5. Сделать один или несколько тестов "провальными", показать вывод в консоль
     и наглядно продемонстрировать разницу между `ASSERT_*` и `EXPECT_*`.

--------------------------------------------------------------------------------
ЧАСТЬ 5.IV: УПРАВЛЕНИЕ СБОРКОЙ ТЕСТОВ ЧЕРЕЗ ОПЦИЮ CMAKE
--------------------------------------------------------------------------------
Требования:
  1. Добавить в корневой CMakeLists.txt опцию (команда `option(BUILD_TESTS ...)`).
  2. При включенной опции (`-DBUILD_TESTS=ON`) тесты скачиваются и компилируются.
  3. При выключенной опции (`-DBUILD_TESTS=OFF`) сборка тестов и скачивание
     Google Test полностью пропускаются, собирается только основная программа.

--------------------------------------------------------------------------------
ЧАСТЬ 5.V: ПЕРЕХОД НА ШАБЛОННЫЕ ФУНКЦИИ (TEMPLATES)
--------------------------------------------------------------------------------
Требования:
  1. Модифицировать проект из 5.IV, заменив функции в библиотеке на шаблонные:
     `template <typename T> double hypotenuse(T a, T b);`.
  2. Теперь функции могут принимать не только `int`, но и `double`, `float` и т.д.
  3. Так как шаблоны функций инстанциируются в момент вызова компилятором,
     библиотека становится "header-only". В CMake такая библиотека объявляется
     как `INTERFACE` (`add_library(hypo_lib INTERFACE)`).

--------------------------------------------------------------------------------
Команда в терминале:

Особенности этого способа:
  - CTest — это стандартная утилита автоматизации тестирования, входящая в CMake.

    в консоль только в том случае, если какой-то тест завершился сбоем.


================================================================================
5. РАЗЛИЧИЯ ASSERT_ И EXPECT_ В GOOGLETEST И ПРОВАЛЬНЫЕ ТЕСТЫ (ПУНКТ 5.III.4)
================================================================================

В Google Test есть два семейства макросов проверки условий: `EXPECT_*` и `ASSERT_*`.
Понимание разницы между ними — ключевой вопрос на защите лабораторной!

+-------------------+-----------------------------------+-----------------------------------+
| Характеристика    | EXPECT_* (например, EXPECT_EQ)    | ASSERT_* (например, ASSERT_EQ)    |
+-------------------+-----------------------------------+-----------------------------------+
| Тип сбоя          | Non-fatal failure (нефатальный)   | Fatal failure (фатальный)         |
| Поведение при     | Регистрирует ошибку, но           | Регистрирует ошибку и НЕМЕДЛЕННО  |
| несовпадении      | ПРОДОЛЖАЕТ выполнение текущего    | ПРЕРЫВАЕТ выполнение ТЕКУЩЕЙ     |
|                   | теста дальше                      | функции теста (делает return)     |
| Когда применять   | Для стандартных проверок данных,  | Когда дальнейшие действия крашнут |
|                   | чтобы увидеть сразу все ошибки    | программу (например, проверка     |
|                   | за один запуск                    | указателя на nullptr перед        |
|                   |                                   | обращением к нему)                |
+-------------------+-----------------------------------+-----------------------------------+

--------------------------------------------------------------------------------
КАК ПРОДЕМОНСТРИРОВАТЬ ПРОВАЛЬНЫЙ ТЕСТ И РАЗНИЦУ:
--------------------------------------------------------------------------------
В файле `tests/test_hypo.cpp` написан наглядный тест:
`TEST(ExpectVsAssertDemo, DISABLED_FailingDemonstration)`

В нем последовательно вызываются:
  1) `EXPECT_DOUBLE_EQ(hypo_basic::hypotenuse(3, 4), 999.0);`
     -> Ожидаем ошибку (5 != 999). Google Test пишет ошибку, но переходит
        к СЛЕДУЮЩЕЙ строке! Строка печати:
        "[ШАГ 2] Сообщение ПОСЛЕ упавшего EXPECT_EQ (тест продолжил работу!)" — ВЫПОЛНЯЕТСЯ!

  2) `ASSERT_DOUBLE_EQ(hypo_basic::hypotenuse(3, 4), 777.0);`
     -> Ожидаем ошибку (5 != 777). Google Test пишет ошибку и НЕМЕДЛЕННО
        ВЫХОДИТ из функции! Строка печати:
        "[ШАГ 4] ЭТО СООБЩЕНИЕ НИКОГДА НЕ БУДЕТ НАПЕЧАТАНО!" — НЕ ВЫПОЛНЯЕТСЯ!

Запустите тест с флагом показа отключенных тестов:
    .\build\tests\hypo_tests.exe --gtest_also_run_disabled_tests

Вы увидите вывод:
    [ RUN      ] ExpectVsAssertDemo.DISABLED_FailingDemonstration
    --- НАЧАЛО ДЕМОНСТРАЦИИ EXPECT vs ASSERT ---
    [ШАГ 1] Выполняем заведомо ошибочный EXPECT_EQ...
    Failure: Expected equality: 5 vs 999
    [ШАГ 2] Сообщение ПОСЛЕ упавшего EXPECT_EQ (тест продолжил работу!)
    [ШАГ 3] Выполняем заведомо ошибочный ASSERT_EQ...
    Failure: Expected equality: 5 vs 777
    [  FAILED  ] ExpectVsAssertDemo.DISABLED_FailingDemonstration
    (Шаг 4 не напечатался, потому что ASSERT мгновенно остановил тест!)

6. УПРАВЛЕНИЕ ОПЦИЕЙ СБОРКИ ТЕСТОВ BUILD_TESTS (ПУНКТ 5.IV)
================================================================================

В корневом `CMakeLists.txt` задана опция:
    option(BUILD_TESTS "Включить сборку модульных тестов Google Test" ON)

И блок условия:
    if(BUILD_TESTS)
        enable_testing()
        add_subdirectory(tests)
    endif()

--------------------------------------------------------------------------------
Как продемонстрировать преподавателю:
--------------------------------------------------------------------------------
1. Сборка с тестами (по умолчанию):
    cmake -B build -DBUILD_TESTS=ON
    cmake --build build
   В логах пишется: "Сборка тестов Google Test ВКЛЮЧЕНА (BUILD_TESTS = ON)",
   и компилируется исполняемый файл `tests/hypo_tests.exe`.

2. Сборка БЕЗ тестов:
    cmake -B build -DBUILD_TESTS=OFF
    cmake --build build
   В логах пишется: "Сборка тестов Google Test ВЫКЛЮЧЕНА (BUILD_TESTS = OFF)",
   папка `tests` вообще не компилируется, Google Test не скачивается,
   а сборка происходит за секунду (собирается только `main_app.exe`).

7. ШАБЛОННЫЕ ФУНКЦИИ И INTERFACE-БИБЛИОТЕКИ CMAKE (ПУНКТ 5.V)
================================================================================

В части 5.V функции библиотеки стали шаблонными:
```cpp
namespace hypo_basic {
    template <typename T>
    double hypotenuse(T a, T b) {
        double da = static_cast<double>(a);
        double db = static_cast<double>(b);
        return std::sqrt(da * da + db * db);
    }
}
```

ПОЧЕМУ ЭТО ВАЖНО В C++ И CMAKE:
1. Шаблонная функция (template) — это не готовый бинарный код, а чертёж/рецепт
   для компилятора. Компилятор может создать реальный код функции только тогда,
   когда видит конкретный тип вызова: `hypotenuse(3, 4)` -> инстанцирует для `int`,
   `hypotenuse(2.5, 6.0)` -> инстанцирует для `double`.
2. Из-за этого тело шаблонных функций ОБЯЗАНО находиться в заголовочных файлах (.hpp),
   чтобы в каждой единице трансляции, где вызывается функция, компилятор видел её тело.
3. В CMake для таких библиотек (header-only) используется специальный тип цели:
   `add_library(hypo_lib INTERFACE)`
   Ключевое слово INTERFACE сообщает CMake:
   - Библиотека не создает отдельный файл .lib / .a / .so / .dll;
   - Но она экспортирует пути к заголовочным файлам через `target_include_directories(hypo_lib INTERFACE ...)`;
   - Любой проект, написавший `target_link_libraries(main_app PRIVATE hypo_lib)`,
     автоматически получает доступ ко всем нужным include-путям!

8. ЧАСТО ЗАДАВАЕМЫЕ ВОПРОСЫ И ОТВЕТЫ НА ЗАЩИТЕ ЛАБОРАТОРНОЙ
================================================================================

ВОПРОС 1: Что такое CMake и зачем он нужен, если есть g++?
ОТВЕТ:
  g++ — это сам компилятор, который превращает .cpp файлы в бинарный код.
  Но в реальных проектах файлов могут быть сотни, плюс используются внешние
  библиотеки, тесты и разные операционные системы (Windows, Linux, macOS).
  CMake — это кроссплатформенный генератор сценариев сборки. Он сам находит нужный
  компилятор, генерирует для него правила сборки (Ninja, Makefiles или проект Visual Studio)
  и управляет зависимостями между модулями.

ВОПРОС 2: Что такое FetchContent в CMake?
ОТВЕТ:
  FetchContent — это стандартный модуль CMake (появился в CMake 3.11), который
  позволяет во время запуска `cmake -B build` автоматически скачать исходный код
  сторонней библиотеки (например, Google Test с GitHub) и включить её прямо
  в дерево сборки текущего проекта с помощью `FetchContent_MakeAvailable()`.
  Благодаря этому студенту или пользователю не нужно вручную ставить Google Test
  в операционную систему.

ВОПРОС 3: Чем отличается STATIC-библиотека от INTERFACE-библиотеки в CMake?
ОТВЕТ:
  - STATIC-библиотека (`add_library(name STATIC ...)`) компилирует свои .cpp файлы
    в бинарный архив объектных файлов (.a в Linux/MinGW, .lib в MSVC), который затем
    линковщик вшивает в итоговый исполняемый файл.
  - INTERFACE-библиотека (`add_library(name INTERFACE)`) не имеет собственных .cpp
    файлов и не создает бинарного архива. Она служит для "header-only" библиотек
    (включая библиотеки с шаблонами) и только передает зависимым целям пути
    к заголовочным файлам и флаги компиляции.

ВОПРОС 4: В чем разница между PRIVATE, PUBLIC и INTERFACE в target_link_libraries?
ОТВЕТ:
  - PRIVATE: зависимость нужна только этой цели, и она НЕ передается дальше по цепочке
    тем, кто будет линковаться с этой целью.
  - PUBLIC: зависимость нужна и этой цели, и передается всем целям, которые зависят от неё.
  - INTERFACE: зависимость нужна только тем целям, которые подключат эту цель к себе
    (сама цель ничего не компилирует).

ВОПРОС 5: Зачем в hypo_random переменные gen, coin, bonus объявлены как static?
ОТВЕТ:
  Ключевое слово static внутри функции означает, что переменная создается и
  инициализируется ровно один раз при первом входе в функцию, а не пересоздается
  при каждом вызове. Это критично для генераторов случайных чисел:
  - Создание std::mt19937 и опрос std::random_device — относительно "тяжелая" операция;
  - Если пересоздавать генератор на каждом вызове, последовательность псевдослучайных
    чисел может повторяться, если вызовы происходят слишком быстро.

ВОПРОС 6: В чем фундаментальное отличие ASSERT_ от EXPECT_ в тестах Google Test?
ОТВЕТ:
  `EXPECT_*` генерирует нефатальную ошибку: отчет помечает тест как упавший, но
  выполнение продолжается дальше по строкам текущей функции теста.
  `ASSERT_*` генерирует фатальную ошибку: немедленно прерывает выполнение текущей
  тестовой функции оператором return. Последующий код в этом тесте не выполняется.
